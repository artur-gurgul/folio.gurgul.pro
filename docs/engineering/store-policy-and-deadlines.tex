\oneliner{Two gatekeepers with different levers. \textbf{Apple} reviews every build against the \textbf{App
Review Guidelines} (90\,\% reviewed in $<$ 24 h) and each spring requires the \textbf{new Xcode/SDK} for
uploads. \textbf{Google Play} runs policy checks and yearly raises the \textbf{target API level}, now also
\textbf{16 KB page-size} support. Knowing the hot-spot guidelines, how to answer a rejection, and the dates
on your calendar is part of senior release ownership.}

\hd{Common rejections — and the fix}
\begin{itemize}
  \item Crash on the reviewer's device / missing demo login / backend down during review $\to$ test the
        Release build on a clean device, put credentials + steps in Review Notes.
  \item Metadata mismatch (screenshots from another version, ``beta'' wording, other platforms' names).
  \item Purpose strings that don't say \emph{why} (``Camera needed'' $\to$ ``to scan receipts'').
  \item Digital goods sold outside IAP; a web wrapper with no native value; Google-only login (4.8).
  \item Demanding personal data the core function does not need (5.1.1(v): ``may not require users to
        enter personal information to function'' unless directly relevant or required by law).
\end{itemize}

\hd{Traps}
\begin{itemize}
  \trap{Discovering the SDK minimum in April from a failed upload — track it with the Xcode upgrade plan.}
  \trap{``OTA lets us ship features without review'' — 2.5.2: fixes yes, new functionality no.}
  \trap{Arguing in the reply instead of showing: a 30-second video beats three paragraphs.}
  \trap{``16 KB is an Android thing, we're RN'' — RN ships \ct{.so} files; you are affected.}
\end{itemize}

\columnbreak

\hd{Answering a rejection}
\begin{enumerate}
  \item Read the cited guideline number; reproduce what the reviewer saw.
  \item \textbf{Misunderstanding} $\to$ reply in App Store Connect's App Review messages: steps, a demo
        video, which screen shows the feature. Polite, specific, no argument about other apps.
  \item \textbf{Real issue} $\to$ fix, resubmit, say what changed in Review Notes.
  \item \textbf{Bug-fix update} blocked by an unrelated older issue $\to$ you may fix that in the
        \emph{next} submission unless it is a legal or safety concern: reply asking to approve this one.
  \item Still disagree $\to$ \textbf{appeal to the App Review Board}: one appeal per rejection, specific
        reasons it complies; answer open questions first.
  \item Urgent: \textbf{expedited review} (critical bug fix with repro steps, or a dated event). 30-min App
        Review appointments exist for grey areas — ask \emph{before} building.
\end{enumerate}

\hd{Google Play specifics}
\begin{itemize}
  \item \textbf{Target API} = \ct{targetSdk}: raising it opts you into new runtime behaviour (API 35:
        edge-to-edge enforced), so budget the work, not just the number.
  \item \textbf{16 KB pages} only matter with native code (\ct{.so}: NDK, RN, most SDKs); Java/Kotlin-only apps
        already comply. AGP $\geq$ 8.5.1, NDK r28+ aligns by default; verify with APK Analyzer, \ct{zipalign -c
        -P 16} or \ct{llvm-objdump -p} (\ct{align 2**14}); test on a 16 KB emulator image.
  \item \textbf{Data safety} form: required for every app, even one that collects nothing; must match the
        app, its SDKs and the privacy policy.
  \item \textbf{Tracks}: internal ($\leq$ 100 testers, minutes, no full review) $\to$ closed $\to$ open $\to$
        production (staged \%). \textbf{New personal accounts} (after 13 Nov 2023): a closed test with
        \textbf{12 testers opted in for 14 days} before production access.
\end{itemize}

\hd{Remember}
\textbf{``Cite the number, show don't argue, fix or appeal once — and put every store date on the release calendar.''}
