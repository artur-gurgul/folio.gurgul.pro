\sheettitle{The JavaScript event loop — browser and Node}{runtime · folio}

\oneliner{One thread runs JS \textbf{to completion}. The browser takes \textbf{one task} from a
queue of its choosing, runs it, then \textbf{drains every microtask}; painting is a task of its
own, queued at each \textbf{rendering opportunity}. Node walks libuv's \textbf{phases} and, after
\textbf{every} callback, drains \texttt{process.nextTick}, then microtasks. Nothing runs between two
microtasks — an endless chain of them freezes everything.}

\section{The processing model (HTML, ECMA-262)}
\begin{itemize}
  \item ECMA-262 leaves scheduling to the host: a job runs only on an \textbf{empty stack}, one at
        a time, to completion; promise jobs in the order queued. HTML: promise job = microtask.
  \item One queue per \textbf{task source}; the browser picks which goes next — order holds
        within a source, not \emph{across} them (a timer vs a message).
  \item Microtask checkpoint after every task \emph{and} every callback that leaves the stack
        empty: between two listeners of a real click, after each rAF and observer callback. It
        drains until empty — \ct{function f()\{queueMicrotask(f)\}} freezes the page; a
        \ct{setTimeout} loop does not.
  \item \textbf{MutationObserver} queues one microtask per batch: 1000 DOM edits in a task → one
        callback, 1000 records; observers called in creation order.
  \item \textbf{Rendering is a task} on the rendering task source (HTML PR \#10007, Jan 2024; before,
        a step of the loop), skipped when nothing visible changed and no rAF is pending. Reading
        \ct{offsetWidth} or \ct{getBoundingClientRect()} after a style write forces style + layout
        inside \emph{your} task.
\end{itemize}

\section{Timers}
\begin{itemize}
  \item HTML: timeout $<$0 → 0; a timer set from a timer task nested more than 5 deep:
        $<$4\,ms → 4\,ms. Earlier timers with an equal or shorter timeout fire first; the browser
        may wait longer (power, throttling).
  \item The IDL type is \ct{long} (signed 32-bit): 2\textsuperscript{31}\,ms ($\approx$24.8 days)
        or more wraps and fires at once. Node: $>$2147483647, $<$1 or NaN → \textbf{1\,ms},
        fractions truncated; Node promises neither exact timing nor ordering.
  \item Chrome, hidden page: timers checked once per second; from Chrome 88, hidden $>$5\,min +
        chain $\geq$5 + silent 30\,s + no WebRTC → once per \textbf{minute}.
\end{itemize}

\section{Trace it}
\begin{lstlisting}[style=js]
console.log('A');
setTimeout(() => console.log('B'), 0);              // task
Promise.resolve().then(() => { console.log('C');    // micro [C]
  queueMicrotask(() => console.log('D')); });       // [F, D]
(async () => { console.log('E');                    // runs now
  await null; console.log('F'); })();               // [C, F]
globalThis.process?.nextTick(() => console.log('G')); // Node
console.log('H');
\end{lstlisting}
\begin{itemize}
  \item \textbf{Browser}: \textbf{A E H C F D B} — D was queued during the drain, still before B.
  \item \textbf{Node, CommonJS}: \textbf{A E H G C F D B} — the tick queue drains first.
  \item \textbf{Node, ES module}: \textbf{A E H C F D G B} — the module body already runs inside the
        microtask drain, so G waits for it to empty.
\end{itemize}
\begin{lstlisting}[style=js]
const b = document.querySelector('button');
for (const n of [1, 2]) b.addEventListener('click', () => {
  queueMicrotask(() => console.log('m' + n)); console.log('L' + n); });
b.click();  // L1 L2 m1 m2 -- this script is still on the stack
            // a real user click: L1 m1 L2 m2
\end{lstlisting}

\section{Node specifics}
\begin{itemize}
  \item Since \textbf{Node 11} (PR \#22842) ticks + microtasks drain after \emph{each} timer and
        immediate callback, ``to better match browser behaviour'' — before, once per list.
  \item \ct{setImmediate} runs its whole queue each iteration; one queued from inside an immediate
        waits for the next — recursive \ct{setImmediate} lets I/O in, recursive \ct{nextTick} or
        microtasks starve it.
  \item \ct{setTimeout(f, 0)} vs \ct{setImmediate} in the main module: either order (has 1\,ms
        passed?). Inside an I/O callback: \textbf{immediate first} — check follows poll.
  \item \ct{nextTick}: before promises in CommonJS, after them in ES modules; \textbf{Legacy}
        since v22.7.0 / v20.18.0 — \ct{queueMicrotask} orders the same in both.
\end{itemize}
\begin{lstlisting}[style=js]
setImmediate(() => { console.log('i1');
  Promise.resolve().then(() => console.log('p'));
  process.nextTick(() => console.log('n')); });
setImmediate(() => console.log('i2'));
// Node >= 11: i1 n p i2        (Node <= 10: i1 i2 n p)
fs.readFile(file, () => { setTimeout(() => console.log('t'), 0);
  setImmediate(() => console.log('i')); });       // always: i t
\end{lstlisting}

\section{Long tasks and yielding}
\begin{itemize}
  \item \textbf{Long task}: a task + its microtask checkpoint $>$\textbf{50\,ms} (so input waits
        $<$50\,ms, inside RAIL's 100\,ms); \textbf{LoAF} (Chrome 123) adds rendering + per-script
        attribution. \textbf{INP} = input delay + processing + presentation of clicks, taps, keys; p75
        $\le$200\,ms good, $>$500\,ms poor; Core Web Vital since 12 Mar 2024.
  \item \ct{await} does \textbf{not} yield — its continuation is a microtask in the same
        checkpoint. To let input and paint in, \textbf{end the task}.
\end{itemize}

\begin{itemize}
  \item \ct{scheduler.yield()}: the continuation keeps the task's priority and signal and runs
        \textbf{ahead} of same-priority tasks. \ct{scheduler.postTask(fn, \{priority, delay,
        signal\})}: \ct{user-blocking} · \ct{user-visible} (default) · \ct{background} (WICG draft).
  \item \ct{setTimeout(r, 0)}: everywhere, back of the queue, clamped once nested.
        \ct{MessageChannel} is unclamped: React's scheduler uses it in browsers (``because of the
        4ms setTimeout clamping''), \ct{setImmediate} in Node, and yields every \textbf{5\,ms}.
        Unchunkable work: a Worker / \ct{worker\_threads} (own loop).
\end{itemize}

const yieldToLoop = () => globalThis.scheduler?.yield ? scheduler.yield()
  : new Promise((r) => setTimeout(r, 0));     // Safari: no scheduler yet
let t = performance.now();                    // inside an async function
for (const it of items) { work(it); if (performance.now() - t < 5) continue;
  await yieldToLoop(); t = performance.now(); }
\end{lstlisting}

\section{React Native}
\begin{itemize}
  \item New Architecture (default since 0.76, Oct 2024): an HTML-modelled loop on the \textbf{JS
        thread} (RFC 0744) — a task, \emph{all} microtasks, then update the rendering (mount new
        Fabric commits). Layout effects run before the mount: \ct{useLayoutEffect} measures and
        repositions in the same frame.
  \item A long JS task delays touches and JS-driven animation; \ct{Animated}'s native driver runs on
        the UI thread — ``the JS thread can be blocked without affecting the animation'' — for
        \ct{transform}, \ct{opacity}, not layout props.
\end{itemize}

\section{Traps}
\begin{itemize}
  \trap{``\ct{setTimeout(0)} runs next'' — every microtask (Node: tick) first, then a 1\,ms floor or 4\,ms clamp.}
  \trap{\ct{el.click()} / \ct{dispatchEvent} from script: listeners run synchronously,
        microtasks only after the calling script.}
  \trap{Hidden tab: rAF stops, timers throttle — no heartbeats or game clocks on them.}
\end{itemize}

\section{Remember}
\textbf{One task → all microtasks → a rendering task when due. Node: phases; nextTick →
microtasks after every callback. Yield = end the task.}
