\sheettitle{Designing login for a mobile app — the whole system}{architecture · folio}

\oneliner{Login is a \textbf{system}, not a screen. An identity step proves \emph{who} (password + MFA,
\textbf{passkey}, SSO); the server issues a \textbf{short-lived access token} and a \textbf{server-side,
revocable refresh credential} bound to \emph{this device}, which the app keeps in the Keychain and
re-opens with \textbf{biometrics}. Refresh, step-up, recovery, logout and rate limits need the same care
as the happy path — attackers pick the weakest one.}

\hd{Session vs token — the real choice}
{\footnotesize
\begin{tabular}{@{}>{\raggedright\arraybackslash}p{13mm}>{\raggedright\arraybackslash}p{28mm}>{\raggedright\arraybackslash}p{30mm}@{}}
\toprule
& \textbf{server session} & \textbf{self-contained JWT} \\ \midrule
credential & opaque random id & signed claims \\
per request & store lookup & signature check only \\
revoke & delete the row: instant & wait for \ct{exp} \\
scales by & shared store & stateless verifiers \\
\bottomrule
\end{tabular}}\par
Mobile default = \textbf{hybrid}: short JWT \emph{access} (stateless, 5–15 min) + opaque \emph{refresh}
stored server-side = the \textbf{revocation point}. Web: HttpOnly cookie session or a BFF — no tokens in JS.

\hd{Re-authentication with biometrics — two designs}
\begin{itemize}
  \item \textbf{A. Biometry-gated secret}: RT in the Keychain with \ct{SecAccessControl}
        \ct{.biometryCurrentSet}; Face ID makes \ct{securityd} release it, then a normal refresh. Simple;
        re-enrolment destroys the item $\to$ full login.
  \item \textbf{B. Device key + challenge} (stronger): at login the app registers a Secure Enclave
        P-256 public key; unlock = server nonce $\to$ SE signs after Face ID $\to$ server verifies $\to$
        tokens. Proves possession \emph{and} presence; a copied RT alone is useless.
  \item Either way biometry is \emph{local}; the server trusts a key, never a \ct{Bool}. Fallback:
        passcode (\ct{.userPresence}) or full login. \ct{touchIDAuthenticationAllowableReuseDuration}
        lets a recent biometric \emph{device unlock} count — not an earlier in-app check.
\end{itemize}

\hd{Device binding \& step-up}
Bind tokens to a key the device holds — \textbf{DPoP} (RFC 9449) proofs, mTLS, or design B — so a
leaked token can't be replayed elsewhere; add App Attest / Play Integrity to vouch for the \emph{app}.
\textbf{Step-up} for money, email or password change: OIDC \ct{max\_age} / \ct{prompt=login} /
\ct{acr\_values}, check \ct{auth\_time}; APIs answer \ct{insufficient\_user\_authentication} (RFC 9470).

\hd{Example — the session store is the revocation point}
\begin{lstlisting}[language=SQLSheet]
CREATE TABLE session (
  id uuid PRIMARY KEY, user_id uuid NOT NULL,
  rt_hash bytea NOT NULL,     -- never the raw token
  family uuid NOT NULL,       -- reuse -> kill family
  device_pubkey bytea,        -- design B / DPoP
  last_used timestamptz, absolute_exp timestamptz,
  revoked_at timestamptz);
-- log out everywhere (also on password reset):
UPDATE session SET revoked_at = now()
 WHERE user_id = $1 AND revoked_at IS NULL;
\end{lstlisting}

\hd{Remember}
\textbf{``Short access, revocable refresh, bound to the device, opened by biometrics — and recovery
as strong as login.''}

\columnbreak

\hd{Identity step — passkeys, SSO, MFA}
\begin{itemize}
  \item \textbf{Passkeys} first: WebAuthn key pair per site, phishing-resistant, nothing to steal
        server-side. iOS: AutoFill sign-in (16) · auto-upgrade after a password login (18) ·
        passkey sign-up \ct{ASAuthorizationAccountCreationProvider} (26). Keep recovery.
  \item \textbf{SSO}: social or enterprise — your IdP \textbf{federates} (OIDC/SAML) and still issues
        \emph{your} tokens; the app talks only to your auth server (\ct{ASWebAuthenticationSession}).
  \item \textbf{MFA strength}: passkey / security key (phishing-resistant) $>$ TOTP (RFC 6238, 30 s)
        $>$ push (\textbf{number matching} vs fatigue) $>$ SMS OTP (SIM swap; NIST ``restricted'').
\end{itemize}

\hd{Brute force \& rate limiting}
Limit per \textbf{account} \emph{and} per IP/device, plus globally; progressive delays + risk
challenges, not hard lockout. \textbf{Credential stuffing}
(breached pairs, one try per account) beats per-account limits — OWASP: MFA is ``by far the best
defense''. Same answer and timing for ``no such user'' and ``wrong password''. \ct{429} (+ \ct{Retry-After}).
\textbf{NIST SP 800-63B-4} (Aug 2025): $\geq$ 15 chars if the password is the only factor ($\geq$ 8 with
MFA), \emph{no} composition rules, \emph{no} periodic change, check a breached/common blocklist,
$\leq$ 100 consecutive failures per account.

\hd{Recovery \& logout}
\textbf{Recovery is the real front door}: single-use short-lived email link or recovery codes, a second
factor if enrolled, a cool-down, a notice to every device; never weaker than login, never reveals
whether an account exists. \textbf{Logout}: \ct{/revoke} the RT (RFC 7009) + wipe Keychain + end the IdP
session (else the next login is silent). \textbf{Everywhere}: revoke all rows, bump the session version;
OIDC back-channel logout tells relying parties.

\hd{Traps}
\begin{itemize}
  \trap{``JWTs can't be logged out'' — put the kill at the refresh token; keep ATs short.}
  \trap{Face ID as \ct{if ok \{ showHome() \}} — gate a key or a secret, not a screen.}
  \trap{Password reset that leaves old sessions alive — the attacker stays in.}
  \trap{Hard lockout after 5 tries = a denial-of-service button.}
\end{itemize}
