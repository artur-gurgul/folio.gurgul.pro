\section{The SwiftUI template (Instruments 26+)}
\begin{itemize}
  \item Contents: the next-generation \textbf{SwiftUI} instrument + \textbf{Time Profiler} +
        \textbf{Hangs} + \textbf{Hitches}. Needs Xcode 26 and a device OS that records SwiftUI
        traces (Instruments 27: iOS 17+ devices only); Command-I (Profile) builds
        \textbf{Release}. The old \emph{View Body} / \emph{View Properties} instruments:
        deprecated, still in the library.
\end{itemize}

\begin{itemize}
  \item Orange / red = how \emph{likely} an update is to cause a hitch or hang — start with red;
        long ones just after launch (the first hierarchy) are normal. Expanded: View Body /

        system); the rest grey.
  \item \textbf{Detail pane}: summary by process $\to$ module $\to$ view type, with counts;
        filter to \emph{Long View Body Updates} or \emph{All Updates}. 26: \emph{Show View

        \textbf{layout passes} + why a layout was \emph{not cached}.
\end{itemize}

\section{Two questions, two workflows}
\begin{itemize}
  \item \textbf{Too long?} Hover the view $\to$ arrow $\to$ \emph{Show Updates} $\to$ Control-click
        one $\to$ \emph{Set Inspection Range and Zoom} $\to$ click the \textbf{Time Profiler}
        track: the call tree (or Flame Graph) of that update only.
        Too few samples in one update: repeat it, then \emph{Show Calls Made by
        \texttt{MyView.body}} merges \emph{every} instance.
  \item \textbf{Too often?} A long Update Group with \emph{no} long update = many short ones.
        \emph{Set Inspection Range} on the group (start it earlier to catch the cause) $\to$
        \emph{All Updates} counts $\to$ hover a view $\to$ \emph{Show Cause \& Effect Graph}.
        A blue $\to$ grey $\to$ blue chain = your code causing an update your own code then
        reacts to (e.g.\ \texttt{onGeometryChange} driving layout): act only past a threshold.
  \item \textbf{Why a body runs} (AttributeGraph): view structs are rebuilt all the time;
        \emph{attributes} keep identity and state. A state change opens a
        \textbf{transaction}; at the next frame it marks that attribute \emph{outdated}, flags
        every dependent (cheap), then recomputes the outdated ones. ``Why did \texttt{body}
        run?'' = ``what marked it outdated?'' \texttt{Self.\_printChanges()} (debug only, best
        effort) names \emph{what} changed, never \emph{who} changed it.
  \item \textbf{Environment}: reading \texttt{@Environment} depends on \emph{all} of
        \texttt{EnvironmentValues} — any change notifies every reader, each checks its value, so a
        skipped body still costs. Keep geometry and timers out of it.
\end{itemize}

\section{Three kinds of hang}
{\footnotesize\setlength{\tabcolsep}{3pt}

\section{Traps}
\begin{itemize}
  \trap{Fix hangs first — that removes many commit hitches too.}
  \trap{One changed property per graph edge: after a fix, record again.}
  \trap{Blocked $\neq$ unresponsive — an idle main thread is blocked; Hangs decides.}
\end{itemize}
