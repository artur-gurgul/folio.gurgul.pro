\sheettitle{React Native CI/CD \& Android signing — build once, promote}{react-native · folio}

\oneliner{An RN pipeline is \textbf{two native builds} (iOS on macOS, Android on Linux) around one JS
codebase, plus an \textbf{OTA lane} for JS-only changes. Make it fast with \textbf{lockfile-keyed caches},
reproducible with \textbf{signing secrets in the CI store} (Android keystore, iOS via match/API key),
and safe by \textbf{promoting the tested artifact} — never rebuilding for release. On Android you
sign with an \textbf{upload key}; Google re-signs with the \textbf{app signing key} it keeps.}

\hd{Build matrix and caching}
\begin{itemize}
  \item Run cheap \textbf{JS checks once} on Linux; build natives only when native inputs changed;
        E2E (Detox/Maestro) on a sim/emulator for main or labelled PRs. macOS minutes cost the most.
  \item \textbf{Cache keys = lockfiles}: \ct{yarn.lock}/\ct{package-lock.json} (\ct{node\_modules} or the
        package cache), \ct{Podfile.lock} (\ct{ios/Pods}), Gradle wrapper + \ct{*.gradle*}
        (\ct{gradle/actions/setup-gradle}). A branch-only key goes stale.
  \item \textbf{Compile less}: prebuilt RN core \ct{.xcframework}s by default since 0.84; \ct{ccache}
        (Podfile \ct{:ccache\_enabled \hbox{=}\hbox{>} true}); Gradle configuration cache (0.79+); one ABI
        (\ct{reactNativeArchitectures=arm64-v8a}) for debug/E2E only — store builds keep all.
\end{itemize}

\hd{Android signing}
\begin{itemize}
  \item \textbf{Play App Signing} is required for new apps (since Aug 2021, AAB): Google holds the
        app signing key; you sign uploads with the \textbf{upload key}. Lost/leaked upload key
        $\to$ \textbf{upload-key reset}; a self-held app key that is lost ends updates.
  \item Key: \ct{keytool -genkeypair -v -storetype PKCS12 -keyalg RSA -keysize 2048 -validity
        10000}; Google: validity $\geq$ 25 years (past 22 Oct 2033).
  \item The RN template signs \textbf{release with the debug keystore} until you add a
        \ct{signingConfigs.release}. Passwords from \ct{\textasciitilde/.gradle/gradle.properties}
        (\ct{MYAPP\_UPLOAD\_STORE\_PASSWORD}\ldots) or CI env \ct{ORG\_GRADLE\_PROJECT\_<name>};
        keystore as a base64 secret decoded in the job.
\end{itemize}

\hd{iOS signing in CI}
Same rules as native: \textbf{match} (\ct{readonly}) or EAS-managed certs, an \textbf{App Store
Connect API key} for upload, temp keychain per job — see signing-and-cicd.

\hd{QA builds before the store}
iOS: TestFlight internal (no review) or ad hoc; Android: Play \textbf{internal testing} track
(up to 100 testers) or Firebase App Distribution; EAS: \emph{internal distribution} builds. Dev
builds (\ct{expo-dev-client}) are for engineers, never for QA sign-off.

\hd{Example — Android release job (GitHub Actions)}
\begin{lstlisting}[language=YamlSheet]
android:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with: { node-version: 22, cache: yarn }
    - uses: actions/setup-java@v4
      with: { distribution: zulu, java-version: 17 }
    - uses: gradle/actions/setup-gradle@v4    # Gradle cache
    - run: yarn install --frozen-lockfile
    - run: echo "$KS" | base64 -d > android/app/upload.keystore
      env: { KS: "${{ secrets.UPLOAD_KEYSTORE_B64 }}" }
    - run: ./gradlew bundleRelease -PversionCode=${{ github.run_number }}
      working-directory: android
      env:  # read by signingConfigs.release as project properties
        ORG_GRADLE_PROJECT_MYAPP_UPLOAD_STORE_PASSWORD: ${{ secrets.KS_PW }}
        ORG_GRADLE_PROJECT_MYAPP_UPLOAD_KEY_PASSWORD: ${{ secrets.KEY_PW }}
\end{lstlisting}

\hd{Versions, OTA, promotion}
\begin{itemize}
  \item \ct{versionName}/\ct{version} is for humans; \ct{versionCode} (integer) and iOS
        \ct{buildNumber} must \textbf{rise on every upload} — derive from the CI run number, or EAS
        \ct{cli.appVersionSource: "remote"} + \ct{autoIncrement: true} (recommended since EAS CLI 12;
        it does not touch \ct{version}).
  \item \textbf{OTA}: each build profile carries a \textbf{channel}; an update reaches only builds
        with the same \textbf{runtimeVersion}. Test on \ct{preview}, then
        \ct{eas update:republish \dd{}destination-channel production} (same bundle); gradual:
        \ct{eas update \dd{}rollout-percentage 10}, \ct{eas update:edit}; undo: \ct{eas update:rollback}.
  \item \textbf{Stores}: TestFlight $\to$ review $\to$ phased release; Play internal $\to$ closed
        $\to$ production with a \textbf{staged rollout} you can halt.
\end{itemize}

\hd{Traps}
\begin{itemize}
  \trap{``Signed release'' that is debug-signed — the template default.}
  \trap{Two CI runs uploading the same \ct{versionCode}: the second is rejected.}
  \trap{A JS-only OTA that needs a new native module crashes old binaries — gate on runtimeVersion/fingerprint.}
  \trap{Rebuilding for production after QA: you ship an untested binary.}
  \trap{Secrets in \ct{EXPO\_PUBLIC\_*} or \ct{.env} end up in the bundle — CI secrets are for the \emph{build}, not the app.}
\end{itemize}

\hd{Remember}
\textbf{``Cache by lockfile, sign with secrets, bump by CI, promote the artifact.''}
