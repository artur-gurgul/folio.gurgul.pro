\sheettitle{VIP · RIBs · MVI · Redux · MV — the architecture map}{design · folio}

\oneliner{Every UI architecture answers three questions — \textbf{who owns the state},
\textbf{which way data moves}, \textbf{where side effects run}. Each pattern below is one set of
answers, and pays for its guarantees in code.}

% ── VIP ────────────────────────────────────────────────────────────────────────────────────
\section{VIP (Clean Swift)}
\noindent\begin{tikzpicture}[sheet]
  \path[use as bounding box] (0,-0.62) rectangle (8,2.08);
  \node[vw] (vc) at (4.0,1.7) {ViewController};
  \node[pr] (pe) at (1.15,0.65) {Presenter};
  \node[lg] (in) at (6.85,0.65) {Interactor};
  \draw[flow] (vc.east) -| node[lbl, right, pos=0.75]{Request} (in.north);
  \draw[flow] (in) -- node[lbl, below]{Response} (pe);
  \draw[hot] (pe.north) |- node[lbl, left, pos=0.3]{ViewModel} node[lbl, above, pos=0.78, text=sheetOrange]{weak} (vc.west);
  \node[rt] (ro) at (1.15,-0.3) {Router \textnormal{\small owned by VC}};
  \node[gy] (wo) at (6.85,-0.3) {Worker \textnormal{\small API, DB}};
  \draw[flow] (in) -- (wo);
  \node[note] at (4.0,-0.3) {one way round};
\end{tikzpicture}

One screen is split into three objects with one job each: the \textbf{ViewController} shows and
forwards taps, the \textbf{Interactor} applies the business rules (calling \textbf{Workers} for API
and database), the \textbf{Presenter} turns results into what the screen displays. Data goes round
\textbf{one way} — Request, Response, ViewModel — so each object is tested alone, by checking what
it hands to the next. The \textbf{Router} opens other screens.
\begin{itemize}
  \trap{VIP is not VIPER: VIPER's Presenter sits \emph{between} View and Interactor and talks both
        ways; VIP's data never comes back the way it went.}
\end{itemize}

% ── MVI ────────────────────────────────────────────────────────────────────────────────────
\section{MVI}
\noindent\begin{tikzpicture}[sheet]
  \path[use as bounding box] (0,-0.5) rectangle (8,1.85);
  \node[vw] (mv) at (4.0,1.5) {View \textnormal{\small\texttt{render(state)}}};
  \node[lg] (mm) at (1.3,0.4) {Model\\[-1pt]\textnormal{\small intent $\to$ new state}};
  \node[pr] (mi) at (6.7,0.4) {Intent\\[-1pt]\textnormal{\small tap $\to$ intent}};
  \draw[flow] (mv.east) -| node[lbl, right, pos=0.75]{taps} (mi.north);
  \draw[flow] (mi) -- node[lbl, above]{intents} (mm);
  \draw[flow] (mm.north) |- node[lbl, left, pos=0.3]{state} (mv.west);
\end{tikzpicture}

One immutable \textbf{State} describes the whole screen. The \textbf{View} only renders it and
turns taps into \textbf{Intents}; the \textbf{Model} turns an intent into the next State. The
screen can show nothing State does not say, so two parts of it cannot disagree, and the same
intents from the same State always give the same screen.
\begin{itemize}
  \trap{A one-off message (a toast) kept in State shows again on every render, until the View
        reports it shown and the State clears it.}
\end{itemize}

% ── MV ─────────────────────────────────────────────────────────────────────────────────────
\section{MV}
No ViewModel: views read \texttt{@Observable} models directly. SwiftUI records which properties
\texttt{body} reads and updates the view only when one of those changes. The logic lives in the
models; keep it out of the views.

\noindent\begin{tikzpicture}[sheet, x=1mm, y=1mm]
  \path[use as bounding box] (0,0) rectangle (80,13);
  \node[vw, minimum width=27mm, minimum height=10mm, align=center] (b) at (66,6.5) {\texttt{body}\\[-1pt]\textnormal{\small\texttt{Text(m.title)}}};
  \node[font=\normalsize\ttfamily, anchor=west, inner sep=0pt] (t) at (0,10) {m.title = "…"};
  \draw[flow, draw=sheetGreen!60!black, very thick] (t.east) ++(1.5,0) -- node[lbl, above, text=sheetGreen!45!black]{\textbf{view updates}} (b.west |- t.east);
  \node[font=\normalsize\ttfamily, anchor=west, inner sep=0pt, text=black!50] (c) at (0,3) {m.count += 1};
  \node[lbl, anchor=west, text=black!55] at (22,3) {nothing: never read};
\end{tikzpicture}
\begin{itemize}
  \trap{Conforming to the \texttt{Observable} protocol alone observes nothing; it takes the
        \texttt{@Observable} macro.}
\end{itemize}

  \draw[hot] (tt.north east) to[bend right=50] (li.east);
  \node[lbl, align=center] at (1.4,-0.12) {R · I · V = Router,\\Interactor, View};
  \node[note] at (4.0,-0.72) {a tree of business logic; views follow · \textcolor{sheetOrange}{orange = reports up}};

The app is a \textbf{tree of RIBs}, each owning one piece of business state. Its
\textbf{Interactor} holds the logic, its \textbf{Router} attaches and detaches child RIBs as that
state changes, and its \textbf{Builder} creates it with its dependencies. The screens follow the
tree, and a RIB can have no view at all: LoggedIn only decides whether OffGame or Game is
attached. A child reports up through a \textbf{Listener} its parent implements; data goes down
as streams.
\begin{itemize}
  \trap{The Router is not navigation: it changes the tree of logic, and the screens follow.}
\end{itemize}

% ── Redux ──────────────────────────────────────────────────────────────────────────────────
\section{Redux}
\noindent\begin{tikzpicture}[sheet]
  \path[use as bounding box] (0,-0.82) rectangle (8,2.12);
  \node[vw] (rv) at (4.0,1.75) {View \textnormal{\small\texttt{subscriber}}};
  \node[gy] (mw) at (6.8,0.98) {Middleware};
  \node[lg] (rr) at (6.8,-0.12) {Reducer \textnormal{\small pure}};
  \node[rt] (rs) at (1.4,0.35) {Store\\[-1pt]\textnormal{\small\textbf{one} app State}};
  \draw[flow] (rv.east) -| node[lbl, above, pos=0.3]{\texttt{dispatch(a)}} (mw.north);
  \draw[flow] (mw) -- (rr);
  \draw[flow] (rr.west) -- (rs.south east);
  \draw[flow] (rs.north) |- node[lbl, left, pos=0.3]{new state} (rv.west);
  \node[note] at (4.0,-0.65) {side effects in middleware, never in a reducer};
\end{tikzpicture}

\textbf{One Store} holds the state of the whole app, and it is read-only. A view changes it only
by dispatching an \textbf{action}; a \textbf{pure reducer} computes the next state from the
current state and the action; every subscriber is then told. Network calls and timers run in
middleware, so the same actions from the same state always give the same state — which is what
makes a bug reproducible.
\begin{itemize}
  \trap{Every subscriber hears every change unless it selects its slice; state only one screen
        uses (an open dropdown) stays out of the store.}
\end{itemize}

% ── TCA ────────────────────────────────────────────────────────────────────────────────────
\section{TCA}
Redux shaped for SwiftUI: every feature has its \textbf{State}, its \textbf{Actions} and a
\textbf{Reducer}, and features compose into one Store. A reducer returns its side effects as
values instead of running them, so a test can check every state change and every effect.
