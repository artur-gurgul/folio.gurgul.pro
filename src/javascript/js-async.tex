\oneliner{A promise is a \textbf{settle-once} result: its executor runs \textbf{now}, its
handlers \textbf{always later}, each as a promise \textbf{job} (a
\link{microtask}{https://developer.mozilla.org/en-US/docs/Web/API/HTML_DOM_API/Microtask_guide}
on the web). \texttt{then} returns a \textbf{new} promise that adopts whatever its handler
returns; \texttt{async}/\texttt{await} runs on the same jobs. The work starts when it is called
and a promise cannot be cancelled — an \texttt{AbortSignal} asks the work to stop.}

\section{Why a promise behaves as it does}
\begin{itemize}
  \item \textbf{Always async, on purpose.} The executor runs synchronously, but \ct{then}
        never calls back synchronously — even on a settled promise the handler waits for a
        \link{job}{https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-promise-jobs}.
        An API that is sometimes sync and sometimes async is impossible to reason about: the 2013
        ``do not release Zalgo'' rule. \ct{Promise.try(f)} (ES2025) closes the gap: a sync throw
        in \ct{f} becomes a rejection.
  \item In \ct{p.then(f, r)}, \ct{r} does not see a throw from \ct{f}; a \ct{catch(r)} after it
        does. A non-function handler lets the value pass; \ct{finally(f)} calls \ct{f} with no
        argument and passes the value on, unless \ct{f} throws.
  \item \textbf{Duck typing is history.} Promise libraries predate ES2015, so a promise adopts
        any
        \link{thenable}{https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise#thenables}
        (a callable \ct{then}), which is read now, called a job later (\ct{t} in drawing 2). So \ct{await \{ then(r) \{ r(42) \} \}} is \ct{42}; a module
        exporting \ct{then} hijacks \ct{await import()}; with \ct{Object.prototype.then} set,
        \ct{async () \fat{} (\{\})} never settles.
  \item \textbf{A promise never holds a promise:} \ct{then} maps \emph{and} flattens. A 2013
        Promises/A+ request for a monadic \ct{then} was turned down as ``typed-language fantasy
        land''. \ct{Promise.resolve(p)} returns a native \ct{p} itself, as \ct{await} does
        since ES2019.
\end{itemize}

Until ES2019
\link{\ct{await}}{https://tc39.es/ecma262/multipage/control-abstraction-objects.html#await}
wrapped every operand in a new promise; tc39/ecma262 \#1250 made it call \ct{PromiseResolve}

\section{async functions}
\begin{itemize}
  \item Run synchronously up to the first \ct{await}; the code after it runs in a later job,
        when state may have changed. \ct{return} / a throw settle the returned promise.
  \item \ct{return await p} beats \ct{return p} twice. In a \ct{try}, \ct{return p} leaves
        before \ct{p} rejects: \ct{catch} never sees it. And V8's async stack traces follow
        \ct{await} only: after \ct{return await} the caller stays in \ct{error.stack}
        (\ct{at async outer}); after \ct{return p} or a \ct{then} chain it is gone.
\end{itemize}

\section{Rejections nobody handles}
\begin{itemize}
  \item The engine only reports: \ct{HostPromiseRejectionTracker(p, "reject")} with no handler,
        \ct{"handle"} once one comes. ``Too late'' is the host's call.
  \item Browser: after a
        \link{microtask checkpoint}{https://html.spec.whatwg.org/multipage/webappapis.html#perform-a-microtask-checkpoint}
        →
        \link{\ct{unhandledrejection}}{https://html.spec.whatwg.org/multipage/webappapis.html#unhandled-promise-rejections}
        (cancelable: \ct{preventDefault()} keeps it off the console); a later handler →
        \ct{rejectionhandled}.
  \item Node only warned until v15; since then
        \link{\ct{--unhandled-rejections}}{https://nodejs.org/api/cli.html#--unhandled-rejectionsmode}
        defaults to \ct{throw}: your \ct{'unhandledRejection'} listener, else an uncaught exception.
\end{itemize}

\section{Combinators are logic}
\link{The combinators}{https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise#promise_concurrency}
(drawing 3): \ct{all} = AND of fulfilments, \ct{any} = OR, \ct{race} = first to settle,
\ct{allSettled} = wait for all. Empty input gives the identities: \ct{all([])} fulfils with
\ct{[]} at once (AND of nothing is true), \ct{any([])} rejects at once with an empty
\ct{AggregateError} (OR of nothing is false), \ct{race([])} never settles (no runner, no winner).

\section{Traps}
\begin{itemize}
  \trap{\ct{pa = getA(); pb = getB(); await pa; await pb} — if \ct{pb} rejects while
        \ct{await pa} waits, it has no handler yet: unhandled (Node: uncaught). Use
        \ct{Promise.all}.}
  \trap{\ct{new Promise(async (resolve) \fat{} …)}: a throw inside rejects only the executor's
        own, unhandled promise; the outer one stays pending.}
\end{itemize}

\section{Concurrency shapes}
\begin{lstlisting}[style=js]
const a = await getA(); const b = await getB();     // tA + tB
const [a, b] = await Promise.all([getA(), getB()]); // max(tA, tB)
items.forEach(async (x) => { await save(x); }); // NOT awaited
for (const x of items) await save(x);             // one at a time
await Promise.all(items.map((x) => save(x)));     // all at once
async function pool(items, n, work) {             // at most n
  const out = []; let next = 0;
  const lane = async () => { while (next < items.length) {
    const i = next++; out[i] = await work(items[i]); } };
  await Promise.all(Array.from({ length: n }, lane));
  return out; }  // next++ is safe: no job runs between read and write
const { promise, resolve, reject } = Promise.withResolvers();
ws.addEventListener('open', resolve, { once: true });
ws.addEventListener('error', reject, { once: true });
await promise;                         // an event as a promise
\end{lstlisting}
One failing lane rejects \ct{pool} at once, yet the other lanes keep pulling items — give
\ct{work} a signal and abort it in \ct{catch}.

\section{Cancel with AbortSignal}
The language has no cancel (TC39 withdrew cancelable promises on 2016-12-15), so
\ct{Promise.race([work, timeout])} stops only the waiting. The DOM's
\link{\ct{AbortSignal}}{https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal} is a flag
the work must choose to check.
\begin{lstlisting}[style=js]
const ac = new AbortController();
const signal = AbortSignal.any([ac.signal, AbortSignal.timeout(5000)]);
const res = await fetch(url, { signal }); // rejects with signal.reason
const sleep = (ms, signal) => new Promise((resolve, reject) => {
  signal?.throwIfAborted();                  // a throw here = rejection
  const stop = () => { clearTimeout(t); reject(signal.reason); };
  const t = setTimeout(() => {
    signal?.removeEventListener('abort', stop); resolve(); }, ms);
  signal?.addEventListener('abort', stop, { once: true });
});
\end{lstlisting}
\begin{itemize}
  \item \ct{abort(reason)} runs the abort algorithms and the \ct{abort} event before it returns.
        The reason travels — \ct{AbortError} by default, \ct{TimeoutError} from \ct{timeout()} —
        so a \ct{catch} tells ``too slow'' from ``cancelled''; \ct{any()} keeps the reason of the
        signal that fired, and cannot unsubscribe from its inputs: remove your listeners.
        Node ships the \ct{sleep} above in \ct{node:timers/promises}.
\end{itemize}

\section{Retry with full jitter}
\begin{lstlisting}[style=js]
async function retry(fn, { tries = 5, base = 100, cap = 10_000, signal } = {}) {
  for (let i = 0; ; i++) {
    try { return await fn(signal); } catch (e) {
      if (i + 1 >= tries || signal?.aborted) throw e;
      await sleep(Math.random() * Math.min(cap, base * 2 ** i), signal); } } }
\end{lstlisting}
Why random: clients that failed together retry together, and plain exponential backoff keeps
them in step — bursts and idle gaps. Full jitter, random(0, min(cap,
base·2\textsuperscript{attempt})), spreads them to a near-constant rate: in a 2015 AWS
simulation with 100 contending clients it more than halved the calls of un-jittered backoff.
Retry only idempotent requests; honour \ct{Retry-After} on 429 / 503.

\section{Async iteration and disposal}
\begin{lstlisting}[style=js]
async function* pages(url, signal) {            // Symbol.asyncIterator
  while (url) {
    const page = await (await fetch(url, { signal })).json();
    yield* page.items; url = page.next; } }
for await (const it of pages('/feed')) if (it.last) break; // -> return()
const all = await Array.fromAsync(pages('/feed')); // ES2026, one by one
\end{lstlisting}
\begin{itemize}
  \item \ct{break} / \ct{throw} in \ct{for await} calls \ct{return()}: the generator's
        \ct{finally} runs. Calls to \ct{next()} queue — one at a time. In an async generator
        \ct{yield v} awaits \ct{v} first.
  \item \ct{for await (x of [p1, p2])} also works, one at a time — a \ct{p2} that rejects while
        \ct{p1} is awaited has no handler yet (the first trap).
  \item \link{\ct{await using r = …}}{https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/await_using}
        (finished, ES2027): at block exit, also on throw, \ct{r[Symbol.asyncDispose]()} (else
        \ct{Symbol.dispose}) is awaited, in reverse order; errors combine into
        \ct{SuppressedError}. \ct{AsyncDisposableStack} holds many.
\end{itemize}
