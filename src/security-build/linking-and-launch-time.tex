\sheettitle{Linking \& launch time}{build · folio}

\oneliner{\textbf{Static} code is copied into your binary at link time (no load cost,
but one copy per binary); \textbf{dynamic} code stays a separate Mach-O that \textbf{dyld} maps,
fixes up and initialises at \emph{every} launch. Launch = \textbf{pre-main} (dyld + runtime
init) + \textbf{post-main} (UIKit + your \texttt{didFinishLaunching} → first frame); aim for
first frame in \textbf{≤ 400 ms}.}

\section{Linking}
\begin{itemize}
  \item \textbf{\texttt{.a}} = archive of \texttt{.o}, static, no resources.
        \textbf{\texttt{.framework}} = bundle (binary + headers + modulemap + resources),
        static \emph{or} dynamic. \textbf{\texttt{.xcframework}} = per-platform slices
        (\texttt{ios-arm64}, \texttt{ios-arm64\_x86\_64-simulator}, …): a fat
        \texttt{lipo} binary cannot hold device-arm64 \emph{and} simulator-arm64.
  \item \textbf{Dynamic} → \emph{Embed \& Sign} (copied to \texttt{App.app/Frameworks},
        found via \texttt{@rpath} = \texttt{@executable\_path/Frameworks}\unverified).
        \textbf{Static} and system frameworks → \emph{Do Not Embed}.
  \item System frameworks sit in the \textbf{dyld shared cache} (pre-linked); \emph{your}
        dylibs pay full load + fixup cost. dyld3/4 cache a launch closure and use chained
        fixups (iOS 13.4+ targets), but many dylibs still hurt.
  \item \textbf{Mergeable libraries} (Xcode 15): framework built with
        \texttt{MERGEABLE\_LIBRARY}, app with \texttt{MERGED\_BINARY\_TYPE} — dynamic
        in Debug (fast iteration), \emph{merged} into the app binary in Release.
  \item Swift binary frameworks need\newline\texttt{BUILD\_LIBRARY\_FOR\_DISTRIBUTION = YES}
        (\texttt{.swiftinterface}, module stability) or only the exact compiler can import them.
\end{itemize}

\section{Launch fixes}
\begin{itemize}
  \item Fewer dylibs (static/merge); no \texttt{+load} (use \texttt{+initialize} or
        explicit init); Swift globals/\texttt{static let} are already lazy — but touching
        one in \texttt{didFinishLaunching} runs its init right there.
  \item Build only the first screen; lazy DI factories; no sync disk/network on main;
        defer SDKs to \emph{after} the first frame, heavy work off the main thread.
  \item Static \texttt{LaunchScreen} is drawn by the system — free; no splash delays.
  \item Profile \textbf{Release}, \textbf{cold}, on a low-end device.
\end{itemize}

\section{Build settings — who wins}
\begin{itemize}
  \item \textbf{Target} = one product; \textbf{configuration} (Debug/Release) = a named
        set of setting values; \textbf{scheme} = which targets + which configuration per
        action (Run/Test→Debug, Profile/Archive→Release by default\unverified). Optimization level
        is a \emph{configuration} setting — ``edit the scheme'' is the wrong answer.
  \item Precedence, highest first: \texttt{xcodebuild SETTING=v} → target (pbxproj) →
        target \texttt{.xcconfig} → project (pbxproj) → project \texttt{.xcconfig} → SDK
        default. Assigning \emph{replaces}; write \texttt{\$(inherited)} to append.
  \item Swift \texttt{\#if DEBUG} reads\newline\texttt{SWIFT\_ACTIVE\_COMPILATION\_CONDITIONS};
        ObjC reads \texttt{GCC\_PREPROCESSOR\_DEFINITIONS} — define it in both.
\end{itemize}

\section{Traps}
\begin{itemize}
  \trap{\textbf{Static + Embed \& Sign} = the code ships twice (inside the binary and in
        \texttt{Frameworks/}); App Store validation may reject it\unverified.}
  \trap{Same static lib linked into a dynamic framework \emph{and} the app → two copies;
        the ObjC runtime warns of a duplicate class, and singletons split.}
  \trap{\emph{``Library not loaded: @rpath/…''} = linked but not embedded.}
  \trap{The linker loads a static-lib member only for a needed symbol: a category-only
        \texttt{.o} vanishes (unrecognized selector); \texttt{-ObjC}\unverified{} loads it.}
  \trap{\texttt{DispatchQueue.main.async} from \texttt{didFinishLaunching} still runs on
        main — it only moves work past the first frame, not off the thread.}
  \trap{\texttt{DYLD\_PRINT\_STATISTICS}: dyld4 no longer reads it; use the App Launch
        instrument. \emph{Prewarming} may create the process and load its dylibs long
        before the tap, so don't time launch from inside \texttt{main}.}
\end{itemize}

\section{Remember}
\textbf{``Static = copy, dynamic = dyld; pre-main is dylibs + initialisers; post-main is
your code; first frame in 400 ms, or the watchdog's \texttt{8badf00d}.''}
