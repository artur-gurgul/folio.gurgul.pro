\oneliner{\textbf{MASVS} v2.1.0 (Jan 2024) is the standard: \textbf{24 controls in 8 groups} saying
\emph{what} a secure app does. \textbf{MASWE} catalogues \emph{how it fails} (78 weaknesses, v1.0.0
Aug 2026), \textbf{MASTG} says \emph{how to test}, and a \textbf{MAS profile} (L1 · L2 · R · P) says
\emph{how much} to test. The \textbf{Mobile Top 10} (2024) is an awareness list of risks, not a checklist.}

\hd{The MAS family}
\begin{itemize}
  \item \textbf{MASVS} = \emph{what} (controls) $\to$ \textbf{MASWE} = \emph{how it fails}
        (weakness IDs \ct{MASWE-0001…0078}) $\to$ \textbf{MASTG} = \emph{how to test}
        (tests, techniques, tools, demos, per iOS/Android).
  \item \textbf{v2.0.0} (Apr 2023) rewrote v1: short, platform-agnostic controls and
        \textbf{no verification levels} in the standard. \textbf{v2.1.0} (Jan 2024) added only
        \textbf{MASVS-PRIVACY} (+ CycloneDX format).
  \item Levels became \textbf{MAS testing profiles} (2026: own ``MAS Profiles'' section):
        \textbf{MAS-L1} baseline for every app · \textbf{MAS-L2} defence in depth for sensitive
        data (banking, health) · \textbf{MAS-R} resilience against reverse engineering +
        tampering, \emph{on top of} L1/L2 · \textbf{MAS-P} privacy. OWASP prefers a profile
        cut from \emph{your} threat model over the defaults.
  \item Same control, different depth per profile: pinning (NETWORK-2) or
        anti-debugging (RESILIENCE-4) are L2 / R territory.
\end{itemize}

RESILIENCE & 1 validates platform integrity · 2 anti-tampering · 3 anti-static analysis · 4 anti-dynamic analysis \\
PRIVACY & 1 minimises access · 2 prevents identification of the user · 3 transparent · 4 user control \\
\bottomrule
\end{tabular}}

\toprule

M2 & Inadequate Supply Chain Security & bad SDKs, build + signing compromise \\

M4 & Insufficient Input/Output Validation & injection via links, WebViews, IPC \\

M6 & Inadequate Privacy Controls & PII over-collected, leaked, undeletable \\

vs 2016: \textbf{credentials}, \textbf{supply chain}, \textbf{input/output validation} and
\textbf{privacy} are new headline risks; 2016's separate authentication and authorization
merged into M3. Top 10 = \emph{what to talk about}; MASVS = \emph{what to verify}.

\hd{How to run the review}
\begin{enumerate}
  \item Inventory: data, entry points (links, IPC, WebViews, push), SDKs, endpoints.
  \item Threat model $\to$ profile: L1 always; L2 sensitive data; +R if the client itself
        holds value; +P personal data.
  \item Map items to controls; run that profile's MASTG tests on both platforms.
  \item Report MASWE-tagged findings; fix server-side first; re-test.
\end{enumerate}

\hd{Traps}
\begin{itemize}
  \trap{``We're MASVS-L2 compliant'' — v2 has no levels; say ``MASVS v2.1, tested
        against the MAS-L2 profile''.}
  \trap{The Top 10 is not a standard you ``comply'' with; audits use MASVS/MASTG.}
  \trap{RESILIENCE never replaces L1/L2: an obfuscated app that logs tokens is still M9.}
  \trap{NETWORK-2 covers endpoints \emph{you} control — not an analytics SDK's host.}
  \trap{M1 is not ``weak passwords'': it is \emph{secrets in the client} — anything shipped is public.}
\end{itemize}

\hd{Remember}
\textbf{MASVS says \emph{what}, MASWE \emph{how it fails}, MASTG \emph{how to test}, the
profile \emph{how much}, the Top 10 \emph{what to talk about}.}
